# E4 - The core in WASM (browser)

The task (roadmap M7): can `notes-core` run in a browser as WASM, at what cost,
and what the next step (the core in a Web Worker) should look like.

**Conclusion: it works, unchanged in output.** The prototype `notes-wasm`
builds every measured note in a Web Worker into HTML byte-identical to the
native build. A WASM build is about as fast as one native thread; it is ~2x
slower in wall time than native only because the two themes no longer build
in parallel. The costs: a 12 MB (brotli) module, of which fonts are almost
half, and memory - a large book needs ~1.5 GB of WASM memory that is never
given back to the browser.

## Method

- The laptop i5-13420H (12 logical CPUs), Arch, Chromium 153 headless
  (`--headless=new`, a fresh profile per scenario), Rust 1.98, Typst 0.15.1,
  `wasm-bindgen` 0.2.129. Other agents built on the same machine during the
  runs: single numbers vary by up to +-30 %, ranges are given.
- The module: `crates/notes-wasm/harness/build.sh` (release, the workspace
  profile: `opt-level = 3`, no LTO; `wasm-bindgen --target web` without the
  name section). Sizes: `harness/sections.py`.
- The browser: `harness/run.mjs` serves the module from localhost, opens
  `index.html`, which starts a module Web Worker (`worker.js` ->
  `measure.js`): `WebAssembly.compileStreaming`, instantiate, the vault and
  the packages handed over as bytes (`WasmCore.addFile`), `open` (fonts,
  themes), then `page(note)` for each note in turn. Memory: the WASM memory
  size after each build (it never shrinks, so it is the peak) and the peak RSS
  (`VmHWM`) of the renderer process.
- Native: `crates/notes-wasm/tests/measure.rs` (feature `measure`) - the same
  `Core` over the same files, release, one process per scenario; wall time,
  CPU time of all threads, `VmHWM`. The page bodies of both are written to
  `tests/.data/wasm/html/` and compared: identical (md5) for all four notes.
- Notes: the "Демо" vault is the user's and not in the repository, so its
  two heavy notes in `tests/vault/демо/` stand for it; the largest repository
  book `tests/vault/Книга` (tiny); and a "Матан"-sized book generated from
  repository notes (`Большая книга`: 2 rounds of 5 chapters - `демо/*`,
  `ассессмент/01-тесты`, `Формулы и теги`, `Сеть/SSH` - labels renamed per
  round): 1.46 MB of page and ~8 s native, against 1.66 MB and 7.4 s of
  "Матан".

With the name section (debug names) the module is 50.7 MB. A smaller build
(`opt-level = "s"`, LTO, `wasm-opt`) was not measured.

**(b) Load**, in the worker, from localhost (no network): compile
(`compileStreaming`) 100-400 ms (V8 compiles lazily: the first build pays for
the rest), instantiate 5-20 ms, handing 0.65 MB of files over 50-130 ms,
`open` (embedded fonts, the theme document) 40-130 ms; WASM memory after open
31.7 MB. Over a network the 12 MB download comes on top.

- WASM time is close to native CPU time: one WASM thread is roughly as fast
  as one native thread (V8 with TurboFan tier-up). The 2x in wall time is the
  lost parallelism: natively the two themes build in two threads and Typst
  lays out in a pool.
- Memory is the same order as natively, but in WASM it **only grows**: after
  `визуализация` and `компоненты` in one worker it is 965 MB and stays so
  (`release_memory` frees the Typst memo inside the module, the browser does
  not get the pages back). An empty renderer is ~300 MB.
- The same book built after its chapters (the memo of the same figures):
  4.3 s native, 10.3 s WASM - an edit rebuild is cheap in WASM too.

**(e) Packages** - CeTZ 0.4.2 + oxifmt 1.0.0 (the whitelist): 0.48 MB of files,
0.12 MB as a brotli tar. In the prototype the host hands them over like vault
files (`addPackageFile`, `preview/cetz/0.4.2/...`).

**(f) Phone**: not available. CDP CPU throttling (`Emulation.setCPUThrottlingRate`)
applies to the page's main thread only: a worker session refuses it ("only
supported for pages"), and the worker ran unthrottled. So the throttled run
builds on the page itself (`run.mjs --throttle 4`, the same code). On-page
baseline without throttling (`--page`), measured under load from other
builds: `визуализация` 12.8 s, `компоненты` 6.9 s, `Большая книга` 36 s;
`Книга` 0.31 s -> 0.90 s at 4x (2.9x). The 4x runs of the heavy notes did
not finish before this report was written: not measured. A guess from the
`Книга` ratio (3-4x): `визуализация` ~30 s, `Большая книга` ~1 min on a
mid-range phone. A 4x estimate is a guess of a mid-range phone: it ignores its memory limits,
and those decide first (below).

## What had to be cfg'd out and why

- `typst-kit`: the workspace now enables only `embedded-fonts` and
  `datetime`; `notes-core` adds `scan-fonts`, `system-files` and
  `system-downloader` for native targets. Without that `fontdb` (mmap,
  fontconfig), `ureq`/`native-tls`/`openssl` and `dirs` do not build or have
  nothing to do in a browser.
- Packages: `world::Packages` - `System` (the Typst package directories and
  downloading, native only) or `Files` (a `Storage` of package files; the only
  one in WASM, default empty). `SharedAssets::packages` gives it to `Notes`.
- Threads: themes compile one after another in the calling thread
  (`world::compile_themes`); the idle memory releaser of `Pages` is not
  started (the host calls `Notes::release_memory`); the warming thread
  priority (`rustix`) is Linux-only anyway.
- `std::time::Instant` panics on `wasm32-unknown-unknown`:
  `notes_core::time::Instant` is `web-time` there (`performance.now()`).
- `getrandom` 0.2 (`rand`, `argon2` in `notes-store`) refuses the target
  without its `js` feature: enabled for WASM only.
- `rust-embed` reads the library and fonts from disk in a debug build:
  `debug-embed` for WASM.
- `notify` and `trash` were already gated off in `notes-store`.
- `chrono` needs `wasmbind` for `datetime.today()` (enabled in `notes-wasm`).

The native build is unchanged: the same features reach native targets, and
native code paths are the same functions.

## What does not work in WASM

- **A Typst panic kills the module**: `wasm32-unknown-unknown` has no
  unwinding, so the "Typst crashed" build error of `world.rs` cannot exist;
  the worker must be restarted (the panic message goes to the console).
- No disk cache, no font chunk cache (`std::fs` returns errors): every start
  builds from scratch; the PDF, PNG, the watcher, the system trash, warming in
  a thread - not available or not tried.
- WASM memory is limited to 4 GB and never returned: a phone browser
  (typically 1-2 GB per tab, a guess) would likely lose the tab on
  `Большая книга`.
- The stack is the default 1 MB (natively compile threads get 64 MB): deeply
  nested markup may overflow. Not hit by the measured notes.

## Recommendations for the Web Worker step

- **Storage: OPFS** behind a `Storage` impl in the worker, via
  `FileSystemSyncAccessHandle` (synchronous, workers only), which fits the
  synchronous `trait Storage`; IndexedDB is only asynchronous and would need
  a full copy in memory (as the prototype's `MemStorage`) plus write-back. A
  guess until measured: OPFS reads per file on every build.
- **Files from the server**: the sync engine needs a blocking HTTP client;
  in a worker that is synchronous `XMLHttpRequest` (sync `fetch` does not
  exist) behind the same `Remote` trait, instead of `ureq`. A guess: fine for
  sync rounds, which are rare.
- **Fonts**: embedded in the module today (5.6 MB of the 12 MB brotli).
  Better: the module without fonts, fonts fetched once as separate files
  (cached by the browser, shared with the client, which already downloads
  WOFF2 parts of the same fonts) and handed to `Fonts` as bytes; Typst's own
  fonts beyond those the themes use (DejaVu, Libertinus, Foxit) can be left
  out. The library (0.16 MB) can stay embedded.
- **Packages: fetched**, the whitelisted versions from the app's own server
  as one archive (0.12 MB brotli), cached; not downloaded from Typst Universe
  (CORS and the whitelist). Bundling them costs only 0.12 MB, so it is also
  acceptable.
- **Warm-up: no** (one thread: warming would block the open note; the module
  cannot stop a build). **The disk cache: yes, in OPFS** - a rebuild from
  scratch costs seconds per note and the page cache format is already bytes.
- **Memory**: one worker per vault, restarted (terminated) after a heavy book
  or above a memory threshold - the only way to give memory back.
- **API transport: the same requests the `Router` serves**, as messages
  `{method, path, body}` -> `{status, body}` in the worker, so the client's
  `app/src/lib/api/` changes only its transport and the HTTP API stays the
  one contract (as the Tauri scheme does, E7). The `Router` itself (axum,
  tokio) was not tried in WASM; a guess: axum builds for wasm32 without the
  server parts, otherwise a small dispatcher over the same core calls.
