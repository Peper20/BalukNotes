# E5 - Память сервера после сборок

Задача: после сборок (прогрев и обычные правки) `notes serve` должен отпускать память и возвращаться ближе к уровню "готового кэша". Цель: <~300 МБ на `tests/vault` в release, без изменения результата рендера и с небольшой ценой на повторное открытие.

## Метод

- Linux, in-process замер: `VmRSS` и `VmHWM` из `/proc/self/status`.
- Фикстура: `tests/vault`, пустой cache dir в `tempdir`, `LibrarySource::Embedded`.
- Путь сборки тот же, что у сервера: `Notes` -> `pages` -> `TypstPipeline` -> `world::Compiler`.
- Тесты:
  - `crates/notes-core/tests/memory_release.rs` (ignored, фича `measure`) - baseline/peak/reopen.
  - `crates/notes-core/tests/memory_release_idle.rs` (ignored) - idle RSS после релиза по простою.
  - `crates/notes-core/tests/memo_regression.rs` (ignored) - цена потери memo на следующую пересборку.

## База до правок

Release, `tests/vault`, пустой cache:

```
baseline_rss_kib=38956 after_warm_rss_kib=1169644 after_edit_rss_kib=1174200 reopen_ms=1 built=21
```

Итого: после прогрева процесс держал около 1.17 ГБ RSS до перезапуска.

## Кандидаты

1) Патч `comemo` в `vendor/` (сжатие емкостей при `evict(0)`).
- Эффект по прошлым dhat-замерам: часть "мертвой емкости" уменьшена, но это не решает весь idle RSS.

2) Релиз памяти по простою в `Pages`.
- Исторически при idle ~1.5 с получали около ~600 МБ.
- При idle 30 с релиз почти не срабатывал в реальной работе.

3) Трюки аллокатора (временный бинарник вне workspace, Linux).

```
baseline: idle_rss_kib=1277228
trim:     idle_rss_kib=1276116 after_trim_rss_kib=1238080
mi:       idle_rss_kib=1351220
both:     idle_rss_kib=1350036 after_trim_rss_kib=1349984
```

Вывод: `malloc_trim(0)` дает только ~38 МБ, `mimalloc` в этом окружении хуже. Это не рабочее решение цели.

## Итоговая реализация

- Один поток releaser на `Pages`.
- Поток использует `Weak` и завершается после drop `Pages` (не держит pipeline живым).
- Релиз выполняется один раз на период простоя: только если была новая сборка после прошлого релиза.
- Порог простоя: `IDLE_RELEASE_DELAY = 5s` (по E5: релиз добавляет ~3-4 мс к следующей пересборке, но 5 с уже срабатывает на практике).

## Вывод и следующий шаг

- Поведение кэша и рендер не меняются.
- Повторное открытие после релиза остается быстрым (1-2 мс), но следующая пересборка большой заметки дороже на ~3-4 мс.
- Idle RSS после серии сборок теперь ~572-576 МБ вместо ~1.17 ГБ, но цель <~300 МБ не достигнута.
- Дальше нужен отдельный разбор удерживаемой памяти (live-объекты: `comemo`, шрифты, библиотеки тем, индекс и т.д.) или архитектурный шаг со сборкой в дочернем процессе.

## Разбор остатка ~575 МБ

Метод: временный бинарник вне workspace (в workspace `unsafe_code` запрещён,
а нужны `mallinfo2`/`malloc_trim` glibc), путь к `notes-core` и **тот же
`[patch.crates-io]` для `comemo`**: без него бинарник собирается с
непропатченным `comemo` и меряет не то (так было в "Трюки аллокатора" выше).
Точки: прогрев `tests/vault` (настройки устройства по умолчанию), простой
5,6 с (релиз), `malloc_trim(0)`, удаление `Notes`. В каждой точке - RSS
(анонимная и страницы файлов) и куча glibc (занято, свободно в аренах,
куски `mmap`); живые объекты по стекам - `dhat` в точке простоя.

Что держит память в простое (до правки ниже):

- живая куча ~180 МБ, из них ~126 МБ - `comemo::accelerate`: вектор
  акселераторов (44 МБ одним куском) и хэш-таблицы в нём (~82 МБ).
  `accelerate::evict` их очищает, но память оставляет (намеренно, для
  частых `evict(N)`); `evict(0)` - тоже. Остальное: регулярные выражения
  подсветки кода (~45 МБ, глобальные, живут всегда), деревья разбора и
  шрифты хранилища (~16 МБ, `Notes`);
- свободные куски внутри арен glibc ~250-350 МБ (фрагментация): живые
  таблицы акселераторов разбросаны по аренам, поэтому `malloc_trim` почти
  ничего не возвращал;
- страницы бинарника ~34 МБ.

Правка `comemo` (`vendor/README.md`): полная очистка (`evict(0)`)
освобождает и акселераторы. Живой кучи в простое - ~72 МБ.

RSS, МБ (release, по 2 прогона; прогрев - ~13 с во всех вариантах):

| Вариант | после прогрева | простой | + `malloc_trim(0)` |
|---|---|---|---|
| glibc, без правки | 659-692 | 558-577 | 446-452 |
| glibc, `MALLOC_ARENA_MAX=2`, без правки | 628-688 | 536-546 | 412-421 |
| jemalloc, без правки | 599-602 | 431-435 | - |
| glibc + правка | 630-631 | 521-561 | 244-265 |
| glibc + правка, `MALLOC_ARENA_MAX=2` | 589-614 | 506 | 165-169 |
| jemalloc + правка | 435-453 | 267-271 | - |

Вывод: остаток - не живые данные, а память, которую аллокатор не вернул
системе. Дочерний процесс не нужен. Выбор пользователя - jemalloc
(`tikv-jemallocator`, глобальный аллокатор бинарника `notes`, кроме MSVC):
возвращает память сам, без `unsafe` в нашем коде.

Настоящий `notes serve` (release, копия `tests/vault`, прогрев всего
хранилища по первому запросу, настройки устройства по умолчанию), RSS, МБ:

| Аллокатор | пик прогрева | простой (через 10 с и дольше) |
|---|---|---|
| glibc (с правкой `comemo`) | 1159 | 633 |
| jemalloc | 1202 | 361 |

Сервер держит больше стенда: кэш страниц (`device.memory`, 64 МБ), части
шрифтов, сервер и наблюдатель.
