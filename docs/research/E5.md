# E5 - Память сервера после сборок

Задача: после сборок (прогрев и обычные правки) `notes serve` должен отпускать память и возвращаться ближе к уровню "готового кэша". Цель: <~300 МБ на `tests/vault` в release, без изменения результата рендера и с небольшой ценой на повторное открытие.

## Метод

- Linux, in-process замер: `VmRSS` и `VmHWM` из `/proc/self/status`.
- Фикстура: `tests/vault`, пустой cache dir в `tempdir`, `LibrarySource::Embedded`.
- Путь сборки тот же, что у сервера: `Notes` -> `pages` -> `TypstPipeline` -> `world::Compiler`.
- Тесты:
  - `crates/notes-core/tests/memory_release.rs` (ignored) - baseline/peak/reopen.
  - `crates/notes-core/tests/memory_release_idle.rs` (ignored) - idle RSS после релиза по простою.
  - `crates/notes-core/tests/memo_regression.rs` (ignored) - цена потери memo на следующую пересборку.

## База до правок

Release, `tests/vault`, пустой cache:

```
baseline_rss_kib=38956 after_warm_rss_kib=1169644 after_edit_rss_kib=1174200 reopen_ms=1 built=21
```

Итого: после прогрева процесс держал около 1.17 ГБ RSS до перезапуска.

## Кандидаты

1) Патч `comemo` в `vendor/` (сжатие емкостей при `evict(0)`).
- Эффект по прошлым dhat-замерам: часть "мертвой емкости" уменьшена, но это не решает весь idle RSS.

2) Релиз памяти по простою в `Pages`.
- Исторически при idle ~1.5 с получали около ~600 МБ.
- При idle 30 с релиз почти не срабатывал в реальной работе.

3) Трюки аллокатора (временный бинарник вне workspace, Linux).

```
baseline: idle_rss_kib=1277228
trim:     idle_rss_kib=1276116 after_trim_rss_kib=1238080
mi:       idle_rss_kib=1351220
both:     idle_rss_kib=1350036 after_trim_rss_kib=1349984
```

Вывод: `malloc_trim(0)` дает только ~38 МБ, `mimalloc` в этом окружении хуже. Это не рабочее решение цели.

## Итоговая реализация

- Один поток releaser на `Pages`.
- Поток использует `Weak` и завершается после drop `Pages` (не держит pipeline живым).
- Релиз выполняется один раз на период простоя: только если была новая сборка после прошлого релиза.
- Порог простоя: `IDLE_RELEASE_DELAY = 5s` (по E5: релиз добавляет ~3-4 мс к следующей пересборке, но 5 с уже срабатывает на практике).

## Вывод и следующий шаг

- Поведение кэша и рендер не меняются.
- Повторное открытие после релиза остается быстрым (1-2 мс), но следующая пересборка большой заметки дороже на ~3-4 мс.
- Idle RSS после серии сборок теперь ~572-576 МБ вместо ~1.17 ГБ, но цель <~300 МБ не достигнута.
- Дальше нужен отдельный разбор удерживаемой памяти (live-объекты: `comemo`, шрифты, библиотеки тем, индекс и т.д.) или архитектурный шаг со сборкой в дочернем процессе.
