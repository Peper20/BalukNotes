# E5 - Server memory after builds

The task: after builds (warm-up and ordinary edits) `notes serve` must release
memory and come back closer to the "ready cache" level. The target: <~300 MB on
`tests/vault` in release, without changing the render result and with a small
cost of reopening.

## Method

- Linux, an in-process measurement: `VmRSS` and `VmHWM` from
  `/proc/self/status`.
- Fixture: `tests/vault`, an empty cache dir in a `tempdir`,
  `LibrarySource::Embedded`.
- The build path is the same as the server's: `Notes` -> `pages` ->
  `TypstPipeline` -> `world::Compiler`.
- Tests:
  - `crates/notes-core/tests/memory_release.rs` (ignored, feature `measure`) -
    baseline/peak/reopen.
  - `crates/notes-core/tests/memory_release_idle.rs` (ignored) - idle RSS
    after the idle release.
  - `crates/notes-core/tests/memo_regression.rs` (ignored) - the cost of a
    lost memo for the next rebuild.

## Baseline before the changes

Release, `tests/vault`, an empty cache:

```
baseline_rss_kib=38956 after_warm_rss_kib=1169644 after_edit_rss_kib=1174200 reopen_ms=1 built=21
```

In total: after the warm-up the process held about 1.17 GB RSS until a
restart.

## Candidates

1) A `comemo` patch in `vendor/` (shrinking capacities on `evict(0)`).
- The effect by earlier dhat measurements: part of the "dead capacity" is
  reduced, but it does not solve all of the idle RSS.

2) An idle memory release in `Pages`.
- Historically with an idle of ~1.5 s we got about ~600 MB.
- With an idle of 30 s the release almost never fired in real work.

3) Allocator tricks (a temporary binary outside the workspace, Linux).

```
baseline: idle_rss_kib=1277228
trim:     idle_rss_kib=1276116 after_trim_rss_kib=1238080
mi:       idle_rss_kib=1351220
both:     idle_rss_kib=1350036 after_trim_rss_kib=1349984
```

Conclusion: `malloc_trim(0)` gives only ~38 MB, `mimalloc` is worse in this
environment. Not a working solution for the target.

## The implementation

- One releaser thread per `Pages`.
- The thread uses `Weak` and ends after `Pages` is dropped (it does not keep
  the pipeline alive).
- The release runs once per idle period: only if there was a new build since
  the last release.
- The idle threshold: `IDLE_RELEASE_DELAY = 5s` (by E5: the release adds ~3-4
  ms to the next rebuild, but 5 s already fires in practice).

This shows that `PageCache` is not the source of the remaining hundreds of
MB.

## Conclusion and the next step

- Cache behavior and rendering do not change.
- Reopening after a release stays fast (1-2 ms), but the next rebuild of a
  large note costs ~3-4 ms more.
- Idle RSS after a series of builds is now ~572-576 MB instead of ~1.17 GB,
  but the <~300 MB target is not reached.
- Next comes a separate analysis of retained memory (live objects: `comemo`,
  fonts, theme libraries, the index etc.) or an architectural step with
  building in a child process.

## Analysis of the remaining ~575 MB

Method: a temporary binary outside the workspace (`unsafe_code` is forbidden
in the workspace, and glibc `mallinfo2`/`malloc_trim` are needed), a path to
`notes-core` and **the same `[patch.crates-io]` for `comemo`**: without it the
binary builds with an unpatched `comemo` and measures the wrong thing (as it
was in "Allocator tricks" above). Points: the warm-up of `tests/vault` (default
device settings), 5.6 s of idle (the release), `malloc_trim(0)`, dropping
`Notes`. At each point - RSS (anonymous and file pages) and the glibc heap
(in use, free in arenas, `mmap` chunks); live objects by stacks - `dhat` at
the idle point.

What holds memory at idle (before the patch below):

- a live heap of ~180 MB, of it ~126 MB is `comemo::accelerate`: the
  accelerator vector (44 MB in one chunk) and the hash tables in it (~82 MB).
  `accelerate::evict` clears them but keeps the memory (deliberately, for
  frequent `evict(N)`); `evict(0)` too. The rest: the code highlighting
  regular expressions (~45 MB, global, always alive), parse trees and vault
  fonts (~16 MB, `Notes`);
- free chunks inside glibc arenas ~250-350 MB (fragmentation): the live
  accelerator tables are scattered across arenas, so `malloc_trim` returned
  almost nothing;
- binary pages ~34 MB.

The `comemo` patch (`.claude/rules/vendor.md`): a full eviction (`evict(0)`)
also frees the accelerators. The live heap at idle is ~72 MB.

RSS, MB (release, 2 runs each; the warm-up takes ~13 s in all variants):

| Variant | after the warm-up | idle | + `malloc_trim(0)` |
|---|---|---|---|
| glibc, no patch | 659-692 | 558-577 | 446-452 |
| glibc, `MALLOC_ARENA_MAX=2`, no patch | 628-688 | 536-546 | 412-421 |
| jemalloc, no patch | 599-602 | 431-435 | - |
| glibc + patch | 630-631 | 521-561 | 244-265 |
| glibc + patch, `MALLOC_ARENA_MAX=2` | 589-614 | 506 | 165-169 |
| jemalloc + patch | 435-453 | 267-271 | - |

Conclusion: the rest is not live data but memory the allocator did not return
to the system. A child process is not needed. The user's choice is jemalloc
(`tikv-jemallocator`, the global allocator of the `notes` binary, except
MSVC): it returns memory by itself, without `unsafe` in our code.

The real `notes serve` (release, a copy of `tests/vault`, a warm-up of the
whole vault on the first request, default device settings), RSS, MB:

| Allocator | warm-up peak | idle (after 10 s and longer) |
|---|---|---|
| glibc (with the `comemo` patch) | 1159 | 633 |
| jemalloc | 1202 | 361 |

The server holds more than the test bench: the page cache (`device.memory`,
64 MB), font parts, the server and the watcher.
