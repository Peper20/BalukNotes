# Архитектура

Приложение для заметок на Typst: красивые заметки в стиле печатного конспекта, всё лучшее
из Obsidian (ссылки, граф, быстрый переход, поиск) и интерактив, которого нет в PDF.
Платформы: браузер, десктоп, Android (iOS — по остаточному принципу).

## Приоритеты

1. **Отрисовка** Typst-заметок в HTML так же красиво, как в PDF.
2. Навигация: дерево, вкладки, быстрый переход, поиск, обратные ссылки, граф.
3. Интерактив: 2D/3D графический калькулятор, анимации, ползунки.
4. Сервер в сети — хранилище и синхронизация (HTTPS, вход); ядро на
   устройствах: десктоп и Android (Tauri), браузер (WASM).
5. Когда-нибудь: встроенный редактор, история версий, бекапы, шифрование.

Заметки пишет в основном Claude Code, приложение их **показывает**. Поэтому
файлы на диске — источник правды, а приложение ничего не меняет молча.

## Решения

### 1. Typst компилирует клиент, сервер — хранилище; интерфейс — Svelte 5 + TypeScript + Vite

Решено пользователем 2026-09-27 (вместо «тонких клиентов» от 2026-09-26):
VPS слабый (1 ядро, 2 ГБ памяти), компилировать там Typst нельзя.

- **Ядро (`notes-core`: компиляция, кэш, индекс ссылок, граф, поиск)
  работает на устройстве**, рядом с интерфейсом. Интерфейс `app/`
  общается с ядром через HTTP API (`notes-server`) — тот же, что сейчас
  у `notes serve`: слой `app/src/lib/api/` знает только адрес.
  - **Компьютер без оболочки** — как сейчас: `notes serve` на своей машине
    и браузер.
  - **Десктоп и Android** — Tauri 2 (десктоп и Android из одного проекта):
    ядро внутри приложения. Интерфейс ходит к нему не через сетевой порт,
    а через свою схему адресов Tauri, которая отвечает тем же `Router`
    axum в процессе приложения: сторонние программы на устройстве до ядра
    не достучатся, токен не нужен. IPC Tauri отдельным API не делаем.
  - **Браузер без установки** — ядро в WASM (Web Worker), транспорт слоя
    API — сообщения воркеру вместо HTTP. Самый трудный вариант: скорость
    и память Typst в WASM на телефоне, шрифты и пакеты (CeTZ) скачиваются
    и хранятся в браузере. Сначала исследование (roadmap, E4).
- **Сервер в сети — хранилище, синхронизация и вход**, без Typst: файлы
  хранилища, версии файлов, события об изменениях, сессии.
- **На каждом устройстве — копия хранилища**, синхронизация с сервером
  (§9): заметки читаются и без сети, Claude Code пишет в копию на
  компьютере.
- Typst — библиотека на Rust, встроена в ядро, версия закреплена в
  `Cargo.toml`: экспериментальный HTML-экспорт не сломается от обновления
  системного `typst`.
- Интерфейс — один на все платформы: **Svelte 5 + TypeScript + Vite**
  (решено 2026-09-26). Почему: фронтенд — оболочка вокруг готового HTML
  заметок; у Svelte самый маленький рантайм (важно для Android WebView),
  меньше всего кода, изоляция стилей из коробки. Типы API — из Rust.
- Клиент берёт адрес ядра из одной настройки
  (`app/src/lib/api/config.ts`: `globalThis.__NOTES_API__`
  до запуска или `configure`); по умолчанию — тот же сервер, что отдал
  страницу. Сейчас там же токен (`notes serve --token`: заголовок,
  `?token=` → cookie `notes_token`); решено заменить его входом с
  сессией (§9), а поле `token` убрать.

```
   компьютер             десктоп / Android (Tauri)     браузер (план)
   браузер: app/         WebView: app/                 app/
      │ HTTP localhost      │ своя схема адресов          │ сообщения
   notes serve           ядро в приложении             ядро в WASM (воркер)
   notes-core            notes-core                    notes-core
   копия хранилища       копия хранилища               копия хранилища
      └──────────────────────────┬─────────────────────────────┘
                                 │ HTTPS: вход, файлы, версии, события
                       ┌─────────┴──────────┐
                       │ сервер (VPS)       │  хранилище · синхронизация · сессии
                       │ без Typst          │  1 ядро, 2 ГБ
                       └────────────────────┘
```

### 2. Хранилище — папка с `.typ`, один Typst-проект

- Данные приложения — каталог пользователя вне репозитория: `--data` /
  `NOTES_DATA`, иначе `data` из `~/.config/baluk-notes/config.toml`, иначе
  `~/.local/share/baluk-notes` (`dirs::data_dir`; `notes info` — где):
  `vault/` — хранилище, `settings.json` — настройки, `cache/` — кэш. Команда
  `notes` работает из любой папки (библиотека, клиент и шрифты встроены). Позже вместо этого будет полноценная база данных; код ходит к
  данным только через `notes-core`, а ядро к файлам хранилища — только
  через `trait Storage` (`notes-core::storage`: каталог — `DirStorage`, в
  тестах — `MemStorage`), поэтому замена затронет одно место.
- Корень хранилища — корень Typst-проекта. Заметки лежат по папкам-областям.
- Библиотека оформления подключается **виртуально**: ядро отдаёт файлы
  `/_baluk/…` из `baluk/` приложения, копии в хранилище нет. Версия
  библиотеки всегда совпадает с версией приложения: в релизе она встроена
  в бинарник. Обычный `typst compile` хранилище не соберёт — PDF делает
  приложение (`notes pdf`, кнопка PDF в клиенте).
- Начало заметки — две строки:
  ```typst
  #import "/_baluk/lib.typ": *
  #show: note.with(title: [SSH])
  ```
  Тема приходит из `sys.inputs.theme`, заметке про темы знать не нужно.
- **Заметка** — один `.typ` файл, компилируется отдельно: быстро, и сломанная
  заметка не валит остальные.
- **Книга** (большой конспект, как «Матан») — папка с `main.typ` и главами;
  отдельная сущность, чтобы главы не считались заметками.
- Книга начинается с `#show: book.with(…)`: главы (`=`) с номерами и
  «Главой N». У заметки `=` — раздел; нумерация и вид шапки настраиваются.
- Ссылки между заметками — `#see("Сеть/SSH", anchor: "Туннели")`: в HTML это
  `<a class="k-link" data-k-target data-k-anchor>`, адрес ставит ядро. Якорь —
  текст заголовка (как в Obsidian) или метка; `id` заголовкам без метки ядро
  выдаёт само: текст заголовка, пробелы и обычная пунктуация → `-`, знаки
  остаются (`C++`, `C#`, `a=b`; в адресе — `%23`). Проверка (`notes check`) идёт по собранным
  страницам (у несобравшейся — по индексу); обратные ссылки и граф — по
  **индексу из исходников** (`notes-core::graph`: парсер Typst находит
  `#see` с буквальными строками, без компиляции; файл разбирается заново,
  только если изменился), дополненному ссылками последней удачной сборки
  каждой заметки (вычисляемые пути).
- **Граф — модуль ядра** (`notes-core::vault_graph`): фильтр (папки, тег,
  ненаписанные, без связей, соседи заметки) и раскладка (силовая модель +
  раздвигание прямоугольников «узел + подпись», детерминированная) — в
  одном месте для всех: клиент берёт готовый граф (`POST
  /api/graph/layout`) и рисует его на главной и на странице `/graph`
  (масштаб, сдвиг, перестановка узлов, поиск); заметка вставляет граф
  функцией `#vault-graph(…)` (`baluk/graph.typ`) — она читает виртуальный
  файл `/_vault/graph/<фильтр>.json` (данные хранилища для заметок —
  реестр поставщиков `notes-core::vault_data`, «префикс → поставщик»; граф
  — первый), CeTZ рисует картинку (PDF, HTML без JS), клиент
  оживляет её по тем же координатам (`lib/live/`). Версия такой заметки
  включает хэш ответа графа: правка, не изменившая граф, её не
  пересобирает. Раскладка — с решёткой для отталкивания и кэшем по
  показанному графу (`vault_graph::Layouts`). Раскладка ядра — покой
  графа: движение (перетаскивание с соседями, переезд при смене фильтра,
  появление) — только в браузере (`graph-physics.ts`, жесты —
  `graph-gesture.ts`, переезды — `graph-motion.ts`), нетронутый граф
  совпадает с картинкой PDF; вернуть её после перестановок — кнопка ↶ на
  `/graph` (плавный переезд к раскладке ядра).
- **Язык заметки** — `lang:` шаблона: слова оформления («Определение»,
  «Рис.», «Глава») берутся из словаря `baluk/i18n.typ` (свои поверх него —
  `words:` шаблона), в HTML — `lang` у `<article>`. Языки словарей
  библиотека выгружает в `css.typ` (`<k-langs>`, вместе с темами), и
  `notes check` предупреждает о `lang:` без словаря и без `words:`. Имена
  API — английские на любом языке.

### 3. Отрисовка — HTML-экспорт Typst

- Текст — настоящий HTML: перенос под ширину экрана, поиск, выделение, якоря.
  Формулы — MathML (рисует браузер). Рисунки CeTZ — `html.frame`, то есть SVG,
  один в один как в PDF.
- В HTML-режиме (`target() == "html"`) библиотека выдаёт элементы с классами
  (`<div class="k-box k-def">`), а вид задаёт CSS (`app/src/baluk-css/`,
  сборка — `assets/baluk.css`). `grid`, `stack`, `place`,
  `v`, `h` HTML-экспорт выбрасывает, поэтому у каждого блока — своя HTML-ветка;
  для кода заметки шаблон ставит страховки: `grid`/`stack`/`place` — SVG-кадр,
  `align` — класс, абсолютные `h`/`v` — пустой `span.k-h`/`div.k-v` с размером
  в переменной (`--k-h`, `--k-v`).
- Из того же исходника собирается PDF (печать, экзамен).

### 4. Темы: минимум две на заметку, переключение без перезагрузки

- Цвета текста, врезок и заголовков — CSS-переменные, `[data-theme=…]`.
- **Рисунки** (SVG) содержат вшитые цвета, и производные цвета (`lighten`,
  `transparentize`) на переменные не заменить. Поэтому заметка компилируется по
  разу на тему, а ядро склеивает результат: текст — из первой компиляции, у
  каждого рисунка — по варианту на тему. Порядок рисунков во всех
  компиляциях одинаковый, так что склейка простая.
- **Обработка HTML — цепочка проходов**: по дереву `typst-html`
  (`notes-core::passes`: темы, якоря, ссылки, скобки формул, теги), по
  тексту сырой страницы (цвета кода) и после кэша, под настройки читателя
  (`notes-core::finish`: рисунки, общие части кадров). Новый проход —
  модуль и строка в списке; время каждого — в логе
  (`RUST_LOG=notes_core=debug`, «проход»).
- **Вес рисунков** (`notes-core::figures`, после склейки, по готовому SVG):
  варианты, различающиеся только цветами, сливаются в один SVG, а
  различающиеся цвета становятся переменными `--kfN` со значениями по темам
  (`<style>` страницы, под меткой `data-k-figs`); глифы подписей — один
  общий `<svg class="k-glyphs">` на страницу; координаты округляются
  (настройка «Рисунки → точность», по умолчанию 0,01 pt) без накопления
  ошибки вдоль пути. Не слилось (другая геометрия, градиенты) — остаются
  варианты, CSS показывает нужный. «Матан»: 3,7 МБ → 1,66 МБ, по сети с
  brotli — 0,21 МБ.
- Обработка рисунков зависит от настроек, поэтому ядро кэширует сырую
  отрисовку (на диске; без кэша на диске — в памяти), а в памяти держит
  одну обработанную копию: смена точности не перекомпилирует заметку, а
  настройки входят в версию страницы.
- Подсветка кода: в HTML-режиме тема подсветки из «опорных» цветов, ядро
  заменяет их на CSS-переменные.
- Новая тема = словарь в `theme.typ`: `css.typ` выгружает её цвета и
  шрифты, CSS-переменные и шрифты для браузера появляются сами.

### 5. Интерактив — веб-компоненты

- Интерактивные рисунки (`baluk/plots.typ`, части — `plots/`): `interactive-plot` и
  `interactive-surface` выдают `div.k-plot` с JSON в `data-k-plot`
  (формулы строкой, диапазоны, параметры) и обычным кадром `canvas` внутри —
  его видят PDF и браузер без JS. Клиент (`NoteView`, реестр `src/lib/live/`)
  монтирует на каждый `.k-plot` компонент `Plot` (SVG для 2D, canvas для
  3D, ползунки) и прячет кадр. Формулу считают и Typst, и клиент — свой
  разборщик того же подмножества Typst в обоих местах (`eval` падал бы на
  делении на ноль); сверка — снимок фикстуры в Vitest. Цвета — переменные
  темы `--k-fig-*`.
- Кадры (`baluk/frames.typ`): рисунок CeTZ с параметром
  компилируется для N значений (≤ 60) в `div.k-frames` с N кадрами
  `div.k-frames-item` (каждый — обычный `canvas`, ядро склеивает темы и
  глифы как всегда). Кадры лежат в одной клетке CSS-сетки — место по
  самому большому; без JS виден кадр по умолчанию. Части SVG, повторяющиеся
  в кадрах (оси, рамка, подписи), ядро выносит в скрытый
  `svg.k-frames-defs` в начале группы (`notes-core::frames`, `<use>` на их
  месте). Клиент (`Frames.svelte`)
  добавляет ползунок, ‹ › и «▶» и переключает `data-current` без
  перерисовки. Считает всё Typst — стиль библиотеки сохраняется полностью.
  В PDF — кадр по умолчанию или ряд выбранных (`pdf: (1, 4, 8)`).
- Живые блоки в клиенте — реестр `app/src/lib/live/` (модуль на блок +
  селектор): новый блок подключается там.
- Дальше (когда-нибудь): анимация алгоритмов и запуск кода.

### 6. Настройки — на стороне клиента, схема — в ядре

- Схема настроек (ключ, группа, подпись, тип, границы, значение по умолчанию,
  **как применить**: атрибут `data-…` или CSS-переменная на `<html>`)
  описана в `notes-core::settings`; клиент рисует форму и применяет вид
  **по схеме** (`appearance.ts`), поэтому новая настройка вида = одна запись
  в схеме + правило CSS.
- Значения хранятся в `settings.json` каталога данных, сервер их проверяет по схеме.
- **Настройки устройства** (группа `device`, признак `device` в схеме):
  прогрев, сборок одновременно, память Typst, пределы кэша — свои у
  каждого устройства, значения по умолчанию — по платформе
  (`settings::Platform`: компьютер / телефон), при синхронизации не
  переносятся; вид — общий. Ядро применяет их на ходу
  (`Notes::apply_device`: при запуске сервера и после `PUT /api/settings`).
- Настройки вида (шапка заметки, нумерация, стиль глав, кегль, ширина колонки,
  тема) применяются в клиенте CSS-атрибутами на `<html>` — без перекомпиляции.
  Поэтому библиотека выдаёт разметку «с запасом» (номера в `span.k-num` есть
  всегда), а прятать или показывать — дело клиента.

### 7. Скорость открытия

- Темы одной заметки компилируются параллельно (поток на тему, кэш файлов
  общий); разные заметки — тоже параллельно (у каждой сборки свой кэш
  файлов из пула, число — настройка устройства, по умолчанию 2): открыть
  заметку, пока собирается книга, можно сразу. Сборка прогрева — темы по
  очереди в одном потоке с пониженным приоритетом.
- Ядро — слои (`notes-core`): `pipeline` (сборка: компиляция по темам →
  отрисовка → рисунки; за `trait Pipeline`), `page_cache` (память + диск),
  `pages` (страница по запросу: сборка заметки — одна, ошибка поверх прежней
  отрисовки), `warm` (прогрев), `notes` — фасад для сервера и CLI. Каждый
  слой проверяется без Typst — подменой сборки и хранилища.
- Кэш в памяти — страницы в LRU с пределом по байтам (64 МБ) плюс
  маленькие записи о каждой известной заметке (версия, файлы, ошибки,
  время сборки): версия и «собрана ли» — без чтения страниц.
- Кэш на диске (`<данные>/cache/pages/<хранилище>/`, `notes-core::cache`): на
  заметку — запись (версия и файлы, ошибки и предупреждения, время
  сборки) и сырая отрисовка отдельным файлом. Годен, если тот же **код
  отрисовки** (метка: версия формата, хэш исходников отрисовки из
  `build.rs`, встроенная библиотека, набор шрифтов) и те же файлы — после
  перезапуска или пересборки сервера книга открывается за десятки
  миллисекунд. Ошибки сборки тоже в кэше. Чистка — при запуске прогрева:
  удалённые заметки, чужие записи старше 14 дней, предел 512 МБ.
- Книга показывается по главам (настройка): собирается целиком (счётчики,
  ссылки между главами), а `GET /api/notes/{id}?chapter=N` (или `?anchor=`)
  отдаёт одну главу — нарезку готового HTML из кэша (`notes-core::book`,
  миллисекунды) со списком глав и картой «якорь → глава». Соседние главы
  клиент берёт заранее (`app/src/lib/chapters.ts`; перед переходом —
  сверка версии книги, чтобы не показать устаревшую главу): «следующая глава» — без
  сервера. Поиск по всей книге — палитра, «Поиск в этой книге»
  (`/api/search?note=`). Вёрстка всей книги
  на телефоне долгая, а по сети глава «Матана» — ~0,2 МБ вместо 1,7 МБ.
  В книге по главам Ctrl+F — тоже поиск по всей книге (номер главы у
  результата — по карте якорей), повторное Ctrl+F — поиск браузера.

### 8. Обновление — по запросу; наблюдатель файлов — только ускорение

- Компиляция ленивая: заметка собирается, когда её запросили, результат
  кэшируется вместе со списком файлов, которые прочитала компиляция.
- Версия заметки — хэш времён изменения и размеров этих файлов (дешёвый
  `stat`), снятых **в момент чтения** компиляцией: файл поправили во время
  сборки — она сразу устарела. Хэш стабильный (SipHash, `notes-core::version`).
  Клиент сверяет версию по кнопке «Обновить», а в режиме «автоматически»
  (настройка `refresh.mode`) — и по событию сервера, и при возврате в
  окно; изменилась — запрашивает заметку, ядро пересобирает.
- **Наблюдатель файлов** (`notes-core::watch`, у сервера): `notify` следит
  за каталогом хранилища (`Storage::watch`) и библиотеки, если она с диска
  (пути `_baluk/…`), изменения раздаются пачкой
  после паузы 100 мс. Индекс ссылок не обходит хранилище, пока ничего не
  менялось (и не реже раза в 10 минут), `DirStorage` помнит список файлов,
  прогрев просыпается от изменения, клиенту уходит событие `GET
  /api/events` (SSE: `hello` — следит ли сервер, `change` — пачка). Клиент
  (`app/src/lib/changes.ts`) на событие сверяет версию; без событий —
  опрос раз в 5 с; в режиме «только по кнопке» — ни того, ни другого.
- Наблюдатель — ускорение, а не источник правды: версии — по-прежнему
  `stat` файлов, постоянной пересборки нет; сломался наблюдатель — всё
  работает обходом, как без него, а после сбоя следующий запрос просто
  соберёт заметку заново. Ошибка компиляции показывается поверх последней
  удачной версии.
- **Прогрев** (`notes-core::warm`, поток сервера): все заметки собираются
  заранее **в кэш на диске** (в памяти не держатся, рисунки не
  обрабатываются — это при открытии) — сначала подсказанные клиентом
  (`POST /api/warm`: вкладки, недавние), затем ещё не собиравшиеся
  заметки (маленькие первыми), затем остальные по времени прошлой сборки,
  новые книги последними; собранное (и с ошибкой) пропускается; ждущий
  запрос пользователя — вне очереди (прогрев не начинает новую сборку).
  Режим — настройка устройства: всё хранилище, только подсказанное
  (открытое) или выключен; после большого прохода (запуск) память Typst
  освобождается — не чаще раза в 10 минут. Проход —
  при запуске, по подсказке, по изменению файлов (наблюдатель) и на всякий
  случай раз в 10 минут (без наблюдателя — раз в минуту). Пропущенное
  просто соберётся по запросу.

### 9. Сервер в сети: хранилище, синхронизация, вход

Пока не сделано (roadmap, M4); решения:

- **Сервер — без Typst** (VPS: 1 ядро, 2 ГБ): хранит файлы хранилища и их
  версии, отдаёт изменения, пускает по сессии. Хранилище — за `trait
  Storage` (каталог, позже — база данных; при нескольких пользователях —
  хранилище на каждого).
- **Синхронизация** — версии файлов + блокировка на редактирование
  (одновременная правка одной заметки не нужна), без CRDT. Устройство
  держит копию хранилища и тянет изменения по событию сервера. Пишет в
  основном компьютер (Claude Code), остальные читают — сначала
  синхронизация «один пишет», блокировка — задел.
- **Вход** (решено пользователем 2026-09-27): один `POST /api/login` с
  паролем → сессия в cookie (`HttpOnly`, `SameSite=Strict`, за HTTPS —
  `Secure`). Токен в адресе не передаётся никогда. У сессии срок — 30
  дней без обращений, каждое обращение его продлевает, истекла — вход
  заново; хэши сессий — на диске сервера (переживают перезапуск).
  Токен один — сессионный, без refresh-токена. `POST /api/logout`
  закрывает сессию. Ядро на устройстве входит так же и хранит свою сессию;
  интерфейс показывает экран входа, когда сервер ответил 401.
- **Хранилище с сервера — недоверенное**: HTML заметки — только
  разрешённые теги и атрибуты, CSP клиента; у сборки — лимиты времени и
  памяти; пакеты Typst — белый список с версиями (roadmap M4).
- История версий и бекапы — на сервере. Шифрование — далеко.

## Риски

- HTML-экспорт Typst экспериментальный: API `html.*` может меняться между
  версиями. Смягчение — закреплённая версия крейта, обновление осознанно, с
  прогоном тестового хранилища.
- Обработка рисунков разбирает SVG от `typst-svg` как текст (формат
  «тег за тегом»). Смена формата при обновлении Typst — повод для тестов
  `figures`; при непонятном входе обработка оставляет рисунок как есть.
- Шрифты оформления (Gentium Plus, JetBrains Mono — `fonts/`, OFL) встроены в
  бинарник вместе со шрифтами Typst и заслоняют одноимённые системные:
  отрисовка не зависит от машины. Браузеру — в WOFF2 и по частям с
  `unicode-range` (`notes-core::webfonts`: подмножество — `fontcull`, WOFF2 —
  `ttf2woff2` с преобразованием `glyf` для TrueType, для CFF — свой
  кодировщик без преобразований): странице на русском нужны латиница и
  кириллица, ~35 КБ на начертание вместо ~0,9 МБ. Математический
  шрифт (CFF + `MATH`) не режется — только WOFF2 (1,3 МБ → 0,66 МБ). Сервер
  сжимает части в фоне при запуске (готовые — из кэша на диске
  `<данные>/cache/fonts`, по хэшу шрифта и части; ненужные части там же
  чистятся).
  Какие шрифты нужны браузеру — основные (первые в списках `font`) шрифты
  тем: `baluk/css.typ` выгружает их вместе с цветами (решено отдавать и
  запасные — roadmap M1).
